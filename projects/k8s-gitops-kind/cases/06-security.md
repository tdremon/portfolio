# 권한은 준 것만, Pod Security는 경고 후 강제, 이미지 스캔은 고칠 수 있는 것만 게이트로

> 보안 기본기 세 가지(RBAC 최소 권한, Pod Security, 이미지 취약점 스캔)를 적용하면 어디서 어떻게 실패하는지 확인했다. 세 가지 모두 실습 자체보다 **적용 순서와 기준을 정하는 판단**에 더 많은 시간과 노력이 들었다.

**조건** 권한 실험은 테스트용 네임스페이스 파드에서 서비스 계정 토큰으로 API 서버를 직접 호출 · Pod Security와 이미지 스캔은 실제 앱(파드 5개)에 적용하며 부하를 계속 보냄 · 공통 [환경](../README.md#환경)

## 실험과 결과

| # | 확인한 것 | 결과 |
|---|---|---|
| 1 | **RBAC** 권한 부여 전후 | 토큰이 유효해도(`/api` 200) 파드 목록 조회는 **403(권한 없음).** `get/list/watch pods` Role을 주자 그것만 200이 되고 `DELETE`, 다른 네임스페이스, `secrets`, 다른 서비스 계정은 계속 403. `auth can-i` 11건이 실제 호출 결과와 모두 일치 |
| 2 | **RBAC** 앱에 적용 | 전용 서비스 계정 + 토큰 마운트 끄기를 롤링 업데이트로 적용했고 그 구간 부하 **75건 전부 `200`.** 앱 파드 안의 토큰 파일이 사라짐 |
| 3 | **Pod Security** `restricted` | `default` 네임스페이스의 파드 6개(앱 5개 + Redis 1개)가 4개 항목을 위반. 앱을 고치는 동안 실패한 롤아웃이 두 번 있었지만 부하 **1,827건 전부 `200`** (세부 내용은 표 아래) |
| 4 | **이미지 스캔**(Trivy) | HIGH+CRITICAL 104건(OS 47 + Python 57). 수정판이 없는 45건을 빼면 **59건이고 그중 57건이 앱 의존성**(대부분 `pillow`). 종료 코드 옵션을 안 주면 104건이어도 `EXIT=0`이라 게이트가 아니고, CRITICAL만 걸어도 `EXIT=1` |

실험 3의 세부 내용:
- `restricted`는 Pod Security의 가장 엄격한 단계이고 `baseline`은 그보다 느슨한 기본 단계다. 앱 파드는 `baseline`은 통과했다.
- `enforce`는 기존 파드는 두고 새 파드 생성만 거부했다.
- `runAsNonRoot`만 적용하면 `CreateContainerConfigError`(숫자 uid 필요), `readOnlyRootFilesystem`만 적용하면 `CrashLoopBackOff`(`/tmp` 필요)가 났다.
- 실패한 롤아웃 동안에도 기존 파드 4개(`maxUnavailable: 1`이라 1개만 내려감)가 서비스를 유지했다.

## 내가 내린 판단

- 토큰은 누구인지만 증명하고, 무엇을 할 수 있는지는 Role이 정한다. 네임스페이스마다 자동으로 생기는 `default` 서비스 계정에는 권한을 붙이지 않고, 필요하면 앱 전용 계정을 만들어 그 계정에만 Role을 바인딩한다. API를 쓰지 않는 앱에는 토큰 자체를 넣지 않는다. EKS에서 파드에 IAM 역할을 붙이는 방식(IRSA, IAM Roles for Service Accounts)도 서비스 계정 단위라서, 다음 프로젝트에서 이 구조를 이어서 확인할 계획이다.
- **Pod Security는 파드가 만들어지는 순간에만 검사한다.** 정책을 바꾼 뒤 `apply`가 성공해도 롤아웃은 실패할 수 있다(거부는 ReplicaSet의 `FailedCreate`로 나타남). 그래서 순서는 `warn`(경고) → 앱 수정 → `enforce`이고, 경고가 0줄이 된 뒤에 강제했다. 경고가 없다고 앱이 뜬다는 뜻도 아니다(`readOnlyRootFilesystem`은 런타임에 죽는다).
- **스캔 숫자를 그대로 게이트에 쓰면 안 된다.** 고칠 방법이 없는 항목까지 막으면 아무도 조치할 수 없다. "지금 고칠 수 있는 것"만 남기고, 조치 대상은 베이스 이미지가 아니라 앱 의존성(`pillow`) 갱신이었다. push 때만 도는 CI로는 이미 배포된 이미지의 새 취약점을 못 잡으므로 정기 재스캔이 필요하다.
