# Redis가 죽어도 API는 계속 응답한다: 캐시 장애를 요청 실패로 번지게 하지 않는 설계

> 추론 결과를 캐시하는 Redis를 0개로 줄여 82초 동안 죽여 보았다. **요청 105건이 전부 `200`**이었고 앱 파드는 재시작도 readiness 변화도 없었다. 응답이 느려질 뿐이었고, Redis를 복구하자 앱을 건드리지 않아도 약 2초 만에 캐시가 다시 동작했다.

> 앱은 캐시가 없으면 직접 추론하도록 설계되어 있다. Kubernetes와 맞닿은 부분은 readiness 검사(`/readyz`)에서 Redis를 빼 둔 것 하나다.

**조건** 앱 파드 5개(캐시 TTL 300초), Redis 1개(영속화 없음), 같은 이미지를 반복 요청하는 부하를 0.5초 간격으로 인그레스 경유 · 공통 [환경](../README.md#환경)

## 실험과 결과

| # | 구간 | 결과 |
|---|---|---|
| 1 | 정상(기준선) | 캐시 적중 응답 0.002~0.009초, 미적중(추론) 0.30초 |
| 2 | Redis 0개 (82초) | 요청 105건 **전부 `200`.** 앱 파드 재시작·endpoint 변화 없음. 캐시를 건너뛰어 응답이 최대 0.283초(추론 시간)로 느려짐. 장애는 앱 로그 `cache get failed` 94줄로 드러남 |
| 3 | Redis 복구 | 앱 조작 없이 **약 2초 만에** 캐시 적중으로 복귀, 요청 135건 전부 `200` |

## 내가 내린 판단

- **캐시 장애가 요청 실패로 번지지 않게 세 가지를 했다.** ① `/readyz`에서 Redis를 제외해 파드가 서비스에서 빠지지 않게 한다. ② 모든 Redis 호출을 예외 처리해 캐시를 건너뛴다. ③ 오류를 메트릭과 로그로 남겨 조용히 무시하지 않는다. 비용은 지연뿐이고, 장애 중 처리 용량은 캐시 덕에 얻던 만큼 줄어든다.
- **클라이언트 라이브러리의 기본값이 장애를 키울 수 있다.** redis-py는 연결 실패를 기본으로 재시도해서 Redis가 없으면 요청당 6~8초가 걸렸다(로컬에서 연결 거부 상태로 측정). 재시도를 끄자 0.01초 이하가 됐다. 이 설정이 없었다면 "응답은 하지만 사실상 멈춘" 장애가 됐을 것이다.
- **같은 날 겪은 별도 장애:** Service를 만들자 파드에 자동 주입된 `REDIS_PORT=tcp://...`가 앱 설정과 겹쳐 앱이 기동 직후 죽었다(`CrashLoopBackOff`). 자동 주입을 끄고(`enableServiceLinks: false`) 환경변수 이름을 바꿔 해결했다.

**한계** 이 클러스터에서는 Redis 파드가 없으면 연결이 즉시 거부된다. 네트워크 단절처럼 연결이 타임아웃되는 장애는 측정하지 않았다. 그 경우 요청마다 앱의 Redis 연결 타임아웃(0.5초)만큼 느려지고, 회로 차단(circuit breaker)이 없어 장애 내내 그 지연이 계속될 것으로 본다.
