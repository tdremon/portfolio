# 롤링 재시작의 5초 지연은 종료 중인 파드로 간 요청이었고, preStop으로 없앴다

> 롤링 재시작 5회 중 4회에서 5초씩 걸리는 요청이 섞여 나왔다. 지연 요청은 모두 파드 종료 직후에 시작됐고, **종료가 시작된 파드로 아직 요청이 들어간 짧은 틈**이 원인이라고 판단했다. `preStop: sleep 5`를 넣자 0회가 됐다. 이어서 종료 중인 파드가 처리 중인 요청을 끝까지 끝낼 수 있는지는 `preStop`, uvicorn timeout, grace 세 값의 관계로 정해진다는 것을 확인했다.

**조건** 롤링 실험: 앱 파드 5개, `maxSurge: 1` / `maxUnavailable: 0`, 부하는 순차 호출 · 종료 실험: 파드 2개, grace 30초, `preStop` 5초, uvicorn timeout 20초, 15초짜리 요청 · 공통 [환경](../README.md#환경)

```mermaid

  A[파드 삭제] --> B[preStop<br/>sleep 5초] --> C[SIGTERM<br/>uvicorn이 처리 중 요청을<br/>timeout까지 대기] --> D[SIGKILL<br/>grace 만료 시]
```

## 실험과 결과

| # | 조작 | 결과 |
|---|---|---|
| 1 | 롤링 재시작 (`preStop` 없음) | 재시작 5회 중 **4회**에서 5초 지연 요청 발생. 지연 요청은 모두 정확히 5.00초였고 파드 종료 직후에 시작됐다 |
| 2 | `preStop: sleep 5` 추가 | 같은 조건에서 **0회** |
| 3 | 설정 누락(ConfigMap 삭제)과 기동 지연 중 롤링 | 새 파드만 실패하고 기존 파드 5개가 유지됨(`maxUnavailable: 0`이라 기존 파드가 먼저 내려가지 않음). 이 실험들을 포함한 **한 번의 부하 실행 전체(2,588건)에서 200 이외 0건** |
| 4 | 15초짜리 요청 중 파드 삭제 | 현재 설정(grace 30초): 15.0초에 정상 응답(`200`) · uvicorn timeout 2초: grace가 남아도 8.2초에 서버 오류(`500`) · grace 10초: 12.1초에 연결 끊김(`000`) |

실험 1의 원인은 인그레스가 대상 목록을 갱신하기 전에 종료 중인 파드로 요청을 보냈다가, 연결 타임아웃(5초) 뒤 다른 파드로 재시도한 것으로 판단했다(인그레스 내부 동작은 직접 확인하지 않음).

## 내가 내린 판단

- **종료 시간은 `preStop + min(uvicorn timeout, 요청 잔여 시간)`이고 grace는 그 위의 상한이다.** 요청이 일찍 끝나면 파드는 grace를 기다리지 않는다(16.6초 ≪ 30초). grace는 넉넉히 두어도 비용이 없지만, uvicorn timeout이 짧으면 grace가 얼마든 소용이 없다.
- **`preStop`도 grace 안에서 시간을 쓰므로 실제 조건은 `preStop + uvicorn timeout + 여유 < grace`다.** 지금은 5 + 20 < 30으로 여유가 5초뿐이고, 가장 긴 정상 요청도 uvicorn timeout 안에 들어와야 한다.
- **실패 모양이 원인을 알려 준다.** 서버가 취소하면 `500`, grace가 모자라 SIGKILL이 오면 응답 없이 `000`이다. 호출 쪽 로그에서 둘은 원인이 다르므로 구분해서 본다. `500` 재시도를 허용한다면 같은 요청이 두 번 처리되는 문제(멱등성)도 봐야 한다.
- 멈춘 롤아웃은 눈에 띄지 않는다(기본 600초 뒤에야 실패 표시). `CreateContainerConfigError`, `CrashLoopBackOff` 알림이 필요하다.

**한계** 종료 실험은 요청 하나로 했고 인그레스를 거치지 않아 대상 목록 제거와 재시도는 보지 않았다.
